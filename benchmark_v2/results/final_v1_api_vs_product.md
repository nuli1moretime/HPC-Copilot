# 纯 API 与最终产品对比（冻结测试集 Final v1）

本页从已完成的 `hpc-copilot-final-v1` 冻结测试中抽取两组结果：

- **纯 API**：同一模型、同一基础提示词，不提供平台知识库，也不调用诊断规则；对应 `llm_only`。
- **最终产品的对话核心**：同一模型，叠加平台知识库检索；对报错题再注入确定性诊断结果；对应 `hpc_copilot`。

模型均为 `deepseek-v4-flash`，temperature=0，30个冻结题完全相同。原始回答、自动评分和冻结指纹均已保存。

## 自动评分结果

| 指标 | 纯 API | 最终产品的对话核心 | 变化 |
|---|---:|---:|---:|
| 总分 | 80.61 | 92.42 | +11.81 |
| 平台问答 | 79.17 | 86.46 | +7.29 |
| 命令解释 | 81.95 | 100.00 | +18.05 |

## 产品相对纯 API 多了什么

1. **107 平台知识检索**：把分区、QoS、模块、Slurm 命令、Apptainer 限制等平台事实注入回答，降低编造平台参数的概率。
2. **确定性报错诊断**：从日志中提取错误类型，并结合固定的排查命令与修复建议；这也是诊断 F1 提升的直接来源。
3. **面向初学者的作业工作流**：产品界面提供作业模板、分阶段执行反馈、状态轮询、日志读取和结果解读，而不只是一次性聊天回答。
4. **平台联动能力**：通过已有 WebShell/Slurm 工作流可提交作业、跟踪状态、读取输出；这类能力需要用真实平台记录补充验证，不能由离线问答分数替代。

## 如何解释脚本生成项没有上升

脚本题的两次调用仍依赖同一个生成模型，且这轮自动评分发现了输出目录和等价表达式等边界问题；最终产品并未在本次离线运行中执行“提交前脚本预检”，因此这里不能宣称已有提升。它应作为下一轮产品改进目标：在用户提交前检查日志目录、分区/QoS、路径、模块和资源配额。

## 答辩可用结论

在项目组自建、30题冻结测试集上，最终产品的对话核心相对纯 API 总分提升 **11.81 分**；其中命令解释提升 **18.05 分**，报错诊断提升 **25.00 分**，诊断 Macro-F1 从 **0.4583** 提升至 **1.0000**。这证明增益来自平台知识与诊断工作流的结合，而不是更换模型。

## 边界

- 这是项目组自建的 107 平台测试集，不是第三方公开 Benchmark。
- “最终产品的对话核心”已涵盖知识库和规则诊断，但不等于完整端到端平台执行测评。
- 作业模板的首次提交成功率、最终状态和关键输出，需要以真实平台运行记录单独展示。
