# 架构检查记录

## 当前判断

整理前的问题不是“技术选型不对”，而是新旧实现同时存在、入口和配置重复，主流程又集中在一个大文件里。第一轮优化后，项目已经收敛到一套 FastAPI + React 实现，适合三人团队继续开发和比赛演示。

## 已处理

- 删除旧 Streamlit 原型与未使用的工具调用循环，避免两套实现继续分叉。
- 后端统一使用 `backend.*` 包路径，启动脚本、Docker 和测试指向同一个应用。
- 敏感凭证不再落盘或写入浏览器长期存储，并清理了副本中的真实配置文件。
- 修正 RAG 已检索但没有传给模型的问题。
- 修正模板取错字段、无法提取 Job ID，以及“离开 squeue 就算成功”的错误判断。
- 模板日志改为读取本次 Job ID 对应的文件，避免把旧日志当成本次结果。
- 用通用 Slurm 入门作业替换 OpenFOAM 案例，使功能与竞赛命题一致。
- 空闲作业监控降低轮询频率；LLM 流式与非流式请求复用 HTTP 连接池。
- 前端把 React、Markdown 和 xterm 拆成独立缓存包，业务包由约 622 kB 降到约 64 kB。
- 自动测试改为覆盖当前后端，并新增凭证持久化和模板 Job ID 回归测试。

## 仍需关注

`backend/main.py` 仍承担接口、聊天路由、模板执行和监控编排，体积偏大，但比赛阶段继续拆分会增加联调风险。下一阶段可以按 `services/chat.py`、`services/template_runner.py`、`services/session.py` 拆出。

更重要的是，连接配置和活跃执行器目前是进程级全局变量。这对单机单用户演示足够，对多人公共部署则可能发生会话串用。多人部署前应引入浏览器会话 ID，并让每个会话持有独立的配置、执行器和清理周期。

RAG 初始化和重建目前仍是全局资源。知识索引可以全局共享，但调用凭证不应共享；多人版本应由服务端统一配置 embedding 凭证，或按会话创建轻量客户端。
